# Démarrage, arrêt et relance des serveurs

## Point d'entrée unique : `startServer(ctx, id, sendLog)` (`startServer.ts`)

Validations (conflits de ports tous jeux confondus, règles du jeu), `getLaunchSpec` (exe, args, env, fichier de log suivi, `prepare`, `logNoise`), log des mods Valheim. Utilisé par l'IPC `server:start` **et** le démarrage automatique ; `restartServer` (même fichier) par `server:restart`, le menu du tray et le redémarrage planifié. **Ne jamais redupliquer cette logique.**

- **`LaunchSpec.prepare`** (`PREPARE` dans `src/main/games/registry.ts`) : exécuté par `ServerManager.start` avant **chaque** lancement, relance après plantage comprise ; un message renvoyé refuse le démarrage. Les préparations propres à un jeu vont là, pas dans `startServer`.
- **Variables d'environnement** : `env` du `serverConfig.ts` du jeu, lues par `getGameEnv()` et conservées pour la relance. Tout démarrage (manuel, redémarrage, planifié) doit passer `getGameEnv(gameType)` (Valheim en a besoin, voir son CLAUDE.md).
- Écrire dans la session de log depuis l'extérieur : `ServerManager.log()`, **après** `start()` (sinon la nouvelle session l'efface).
- Mise à jour du jeu d'un serveur donné (pas du serveur actif, contrairement à l'IPC `steamcmd:updateGame`) : `serverUpdate.ts` (`checkServerUpdate`, `updateStoppedServer`), utilisé par le redémarrage planifié et les actions groupées.

## Démarrage automatique (issue #57)

- ⚠️ **Jamais en dev** : `autoStartServers` ne fait rien quand `!app.isPackaged` (sauf `NEXUM_DEV_AUTOSTART=1`) : `yarn dev` partage le dossier de données de l'app installée, donc ses vrais serveurs, qu'il couperait net à la fermeture.
- Par serveur (`Server.autoStart`, case dans `ServerDialog`). Tourne **après** `tryAdoptAll` (promesse `adoption`, `ipc/handlers.ts`) : un serveur adopté n'est pas relancé. Démarrages espacés de 5 s.
- **Échec d'un démarrage tenté par Nexum seul** (démarrage auto, relance après plantage) : `ServerManager.logStartFailure` + `notifyStartFailed` (`serverAlerts.ts`). ⚠️ Pas `log()` / `mgr.log()` : le refus arrive avant toute session (validations de `startServer`, exe absent, `prepare`) ou après la fermeture de la session plantée, et `SessionLogStore.line` ignore une ligne hors session. `logStartFailure` ouvre une courte session à lui (listée sur la page Logs, exportée), **sans vider la vue en direct** (`SessionLogSink.begin(false)`, pas de `server:logSession`) : après un plantage, les lignes qui en donnent la cause restent affichées au-dessus de l'échec de la relance. Puis `server:autoStartFailed` (`AutoStartFailedNotice`, erreur codée brute traduite par le renderer) → toast « Voir les logs », et notification Windows si la fenêtre n'est pas regardée.

## Relance après un plantage (`crashRestart.ts`, `registerCrashRestart`, `Server.autoRestart`)

- `ServerManager` appelle `onCrash` (via `ServerManagerRegistry.onCrash`) quand le serveur s'arrête seul avec une erreur (statut `crashed`, lancé **ou** adopté), **avant** la fermeture de la session : « Relance automatique dans 10 s » et l'abandon vont dans son `.crashed.log` (issue #146).
- Relance par `startServer` 10 s plus tard, sauf serveur supprimé, option décochée ou relancé à la main entre-temps. Au plus 3 relances en 30 min, puis abandon écrit dans les logs et `notifyGaveUp` : événement `server:autoRestartGaveUp` (`AutoRestartGaveUpNotice`) → toast « Voir les logs » (`hooks/useServerNotices`), plus une notification Windows si aucune fenêtre n'est visible et au premier plan.
- Alertes d'un serveur : `serverAlerts.ts` (`notifyGaveUp`, `notifyStartFailed`, `alertIfUnwatched` : textes `trayStrings.ts`, clic → `showWindow`, référence gardée sinon le ramasse-miettes perd le `click`).
- Compte rendu `autoRestarted` écrit **après** `startServer`, dans la nouvelle session ; `autoRestartFailed` par `logStartFailure` (voir plus haut).

## Surveillance : démarrage bloqué et RAM (`Server.stuckStartMinutes`, `Server.ramLimitGb`)

- Ligne « prêt » par jeu (`READY_LINES`, `src/main/games/registry.ts`, `LaunchSpec.readyLine`), testée dans le `log` de `ServerManager.beginSession` (lignes brutes, avant le filtre de bruit) ; `getStartup()` → `{ startedAt, ready }`. ⚠️ Seulement des lignes vérifiées sur une vraie install (ARK, Enshrouded) : un jeu sans ligne n'a pas l'option (un faux « pas prêt » tuerait un serveur sain). Serveur adopté : prêt d'office. Le renderer sait qu'un jeu a la ligne par `GamePlugin.startupReadyHintKey`.
- `stuckStartWatch.ts` (30 s) : pas prêt après N min → `kill()` (pas un plantage) puis `startServer` 10 s plus tard ; une seule fois par lancement (`handled`, clé serveur + `startedAt`). Compteur **partagé** avec la relance après plantage (`restartAttempts.ts`, 3 en 30 min) : au-delà, laissé arrêté.
- Délai proposé 20 min (`src/shared/watchdog.ts`) : le 1er démarrage d'ARK avec de nouveaux mods ou après une mise à jour est long, 10 min tuaient un serveur sain. Relance réussie → ligne `stuckStartRestarted` dans la nouvelle session ; échec → notice `stuckRestart`.
- RAM : `src/main/monitor/ramWatch.ts` (voir `src/main/monitor/CLAUDE.md`), redémarrage par `runScheduledRestart` (installe aussi la mise à jour du jeu si `updateGame` est coché) (annonces de la Planification si le jeu sait prévenir, sinon tout de suite : sans client, le compte à rebours attendait les 30 min pour rien).
- Dernier événement par serveur gardé dans le main (`watchdogEvents.ts`, IPC `server:watchdogEvent` / `dismissWatchdogEvent`, poussé par `server:watchdog`) : `components/server/WatchdogAlert.tsx` sous l'en-tête du Dashboard (un toast se perdait au rechargement) ; notification Windows par `notifyWatchdog` (`serverAlerts.ts`).
- La ligne « Arrêt forcé demandé depuis le Dashboard » est écrite par `adminActions.killServer`, pas par `kill()` (aussi utilisé par la surveillance).

## Priorité et cœurs du processeur (`processTuning.ts`, `Server.cpuPriority`, `Server.cpuCores`)

- Un seul PowerShell par application (`PriorityClass`, `ProcessorAffinity`), sur le processus racine **et ses enfants directs** sauf `conhost.exe` (sinon compté dans « N processus ») : c'est le `…-Shipping.exe` qui travaille (Palworld, Astroneer, Dragonwilds). Vérifié sur un faux lanceur qui crée son enfant 3 s après : réglages hérités/appliqués aux deux.
- Appliqué après un démarrage réussi (`startServer` **et** `restartServer`) puis de nouveau 15 s plus tard (⚠️ un enfant déjà créé ne prend pas les réglages appliqués ensuite au parent, et la priorité n'est héritée que pour Basse / Sous la normale) ; après l'adoption (`ipc/handlers.ts`, `adoption.then`). Ligne écrite la 2e fois seulement si un enfant s'est ajouté. Rien avec les réglages par défaut ; abandonné si le PID a changé.
- Accès refusé (serveur admin, autre utilisateur) : ligne `processTuningFailed`, le démarrage n'est jamais bloqué. Masque limité aux 64 premiers cœurs (un groupe de processeurs). Cœurs pas transférés entre PC (`transferFormat.ts`). Formulaire : `cpuCores: []` = tous (jamais `undefined`, que l'IPC omettrait).

## Messages de fin (`exitText`, `src/main/i18n/logStrings.ts`)

Code NTSTATUS (≥ `0xC0000000`) affiché en hexadécimal et nommé (`crashNames`) avec « erreur du jeu lui-même, pas de Nexum ». Sauf `0xC000013A` (STATUS_CONTROL_C_EXIT : console fermée ou CTRL+Pause) → `consoleClosed`, pas « planté » (la relance s'applique quand même). Autres codes : « Le serveur s'est arrêté (code N) ».

## Arrêt (`ServerManager.stop`, `getStopConfig` de chaque jeu)

- Quatre mécanismes : API (Palworld, `restApiEnabled`), RCON (ARK, `StopConfig.rcon`), signal console `gracefulSignal: "ctrlBreak"` (Valheim, Enshrouded ; `sendConsoleSignal`, `windowsCtrlC.ts`, `AttachConsole`/`GenerateConsoleCtrlEvent`), sinon `taskkill` (Astroneer, Dragonwilds : `restApiEnabled: false` sans signal). Signal ignoré → `taskkill` après 30 s.
- API et RCON passent par `createGracefulShutdown` (`shutdownClient.ts` : client, lignes de log, `exitTimeoutSeconds`) : annonce, sauvegarde, demande d'arrêt, attente de la fin. Palworld sans délai garde l'ancien comportement (pas d'attente, puis `taskkill`).
- ⚠️ ARK n'a pas d'arrêt différé (`nexumWaitLine`) : le délai annoncé est attendu dans `stopViaApi` avec `waitForExit` (fin dès que le processus meurt : rien à arrêter, jamais de `taskkill` sur un PID mort, que Windows a pu réattribuer, `processGone`), puis `DoExit` et jusqu'à 120 s d'attente (`ARK_EXIT_TIMEOUT_SECONDS`) : `DoExit` sauvegarde le monde (~20 s), un `taskkill` à ce moment la perdrait. `hurryStop()` saute le délai : la garde de fermeture l'appelle pour un serveur déjà en cours d'arrêt (`quitGuard.ts`, attente max 130 s), sinon on quittait au bout de 45 s et le serveur, tué avec Nexum, perdait sa sauvegarde.
- ⚠️ **CTRL+Pause, pas CTRL+C** : un serveur lancé par Nexum ignore CTRL+C (attribut « ignorer CTRL+C » probablement hérité du parent, `SetConsoleCtrlHandler(NULL, TRUE)`), alors que CTRL+Pause ne peut pas être ignoré ainsi. Valheim : « OnApplicationQuit » → « World save (5/5) done », code 0, ~3 s.
- **Tuer** (`ServerManager.kill`, menu « ⋯ » du Dashboard) : `stop({})`, donc `taskkill` avec le statut `stopping`. ⚠️ Sans `hurryStop()` : un arrêt ARK en attente enverrait `DoExit` (début de sauvegarde) juste avant le taskkill. Un redémarrage en cours continue (choix produit : Tuer débloque son arrêt). ⚠️ Ne pas appeler `forceKill` directement sur un serveur `running` : la fin serait lue comme un plantage (`crashed`) et relancée par `crashRestart.ts`.
- **Commandes du Dashboard** (`adminActions.ts`, IPC `server:capabilities` / `saveNow` / `sendMessage` / `kill`, `serverId` explicite) : sauvegarde par `getGameSaveRequest` (`src/main/games/saveRequests.ts` ; Palworld sans `AdminPassword` = API désactivée, sinon 401), message par le client de `createGracefulShutdown` (comme les annonces de redémarrage) ; `GracefulShutdown.asciiChat` dit au renderer que le jeu retire les accents (ARK, `src/shared/chatText.ts` partagé pour l'aperçu).
- **Détection de fin** : processus lancé par Nexum → lue sur le `ChildProcess` (`close` / `exitCode`), **jamais** via `si.processes()` (liste en retard ou en échec → « vivant » → `taskkill /F /T` sur un serveur déjà fermé, voire sur un autre programme si le PID est réattribué). `ensureStopped` / `waitForPidExit` / `pidExists` ne servent qu'aux processus **adoptés**.

## Vérifications au démarrage (jamais attendues)

- **Version du jeu** (`gameUpdateCheck.ts`, `checkGameUpdateOnStart`) : après un `start()` réussi (bouton et démarrage auto, pas les redémarrages). Réutilise `SteamCMD.checkForUpdate`. Choix produit : **avertir seulement**. ⚠️ Rien n'est signalé si `requiredBuild` est `null` (Steam injoignable, timeout, SteamCMD absent…) : le repli renvoie `upToDate: false`, ne jamais le lire comme « pas à jour ». Résultat dans la session (`ServerManager.log()`) et, si MàJ, `server:gameUpdateAvailable` (`GameUpdateNotice`) → `hooks/useServerNotices` (bouton « Mettre à jour » → Installation ; `notify()` accepte une `action`, 15 s).
- Install de la **bibliothèque Steam** (`isSteamLibraryInstall`) : `UpdateCheckResult.steamLibrary = true` → « mettez-le à jour depuis Steam », sans bouton.
- **Build installé** (`getInstalledBuildId`, `src/main/steamcmd/`) : manifest du client Steam (`<bibliothèque>/steamapps/appmanifest_<appId>.acf`) et celui de SteamCMD (`<serveur>/steamapps/`) peuvent coexister : on garde le **plus récent** (`LastUpdated`, sinon date du fichier). Préférer toujours celui de la bibliothèque faisait annoncer la mise à jour en boucle après une MàJ faite depuis Nexum.
- **Mise à jour d'un ancien build installé par un autre outil** (`steamcmd/deniedManifest.ts`) : SteamCMD redemande le manifeste du build installé, que Steam refuse en anonyme (`Failed to get manifest request code, 'Access Denied'` dans `logs/content_log.txt`). La mise à jour est annulée avant tout téléchargement : `state is 0x6`, code 7, et `validate` n'y change rien. ⚠️ Détecter par `content_log.txt` (partie écrite par ce lancement), pas par `0x6`, qui sort pour d'autres échecs. `runInstall` met alors `<serveur>/steamapps/appmanifest_<appId>.acf` de côté (`.nexum-old`) et relance une fois : installation neuve par-dessus les fichiers, vérifiés, `Saved` intact (vérifié sur ARK : build de 2024 → 9,4 Go retéléchargés). Jamais pour la bibliothèque Steam (manifeste du client Steam). Échec du 2e essai : `STEAMCMD_OLD_BUILD_DENIED` seulement si le refus revient (sinon disque plein ou réseau : `STEAMCMD_FAILED`). Un `.nexum-old` resté d'un 2e essai interrompu est réglé au début de l'installation suivante. Accepté : deux mises à jour SteamCMD simultanées partagent le journal, le refus de l'une peut déclencher chez l'autre un 2e essai inutile (long, sans perte).
- **Mods Valheim** : `checkModUpdatesOnStart`, voir `src/main/games/valheim/CLAUDE.md`.
- Ces vérifications contactent Steam / les registres : déclarées dans `docs/code-signing*.md`.

## Carte « Rejoindre le serveur » (`joinInfo.ts`)

IPC `server:getJoinInfo`, `server:getPublicIp` ; composant `components/server/JoinServerCard.tsx`.

- IP locale + port de jeu + ports UDP à rediriger (`getGamePorts`, `forward: true` uniquement, jamais RCON/REST ; `formatPortRange` → `2456-2458` ou `7777, 8888`), code crossplay Valheim lu dans les logs (`join code X`), nom à chercher dans le jeu (`JoinInfo.searchName`, `SEARCH_NAMES` dans `src/main/games/registry.ts`).
- **IP publique uniquement au clic** (`api.ipify.org`, cache 10 min, déclaré dans `docs/code-signing*.md`) : jamais automatiquement.
- `localIpv4()` classe les cartes réseau au lieu d'exclure par nom : ⚠️ un commutateur Hyper-V **externe** « vEthernet (…) » porte la vraie IP du PC ; seuls « Default Switch », WSL, VirtualBox, VMware, VPN… sont pénalisés. Préférence 192.168.x.x > 10.x > 172.16-31.
